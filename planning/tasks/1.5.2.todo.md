# 5.1.2 -- Per-grid-latitude search sizing; independent brute-force tests

## Goal

Size each grid point's index search from its own latitude (not the mean input latitude) in both KDE functions, and pin both KDE paths to an independent brute-force R reference at relative tolerance 1e-10.

## Notes

Facts from Analysis (`src/rust/src/lib.rs`, 374 lines):
- `geodesic_kde_rust` index setup: lines ~37-75 (`central_lat`, `km_per_lon_degree = 111.32*cos`, `search_radius_lon_deg = 3bw / km_per_lon.abs().max(0.1)`, `search_radius_lat_deg`, `search_radius_deg = max`, `index_cell_size = clamp(1.5*search_radius_deg, 0.1, 45)`). Index build lines ~77-100 with wrapped keys for `x > 90` (`-360`) and `x < -90` (`+360`). Cell loop lines ~104-140, symmetric `search_radius_cells = ceil(search_radius_deg/cell)`.
- `geodesic_kde_adaptive_rust` (lines ~168-294): pass 1 calls `geodesic_kde_rust` for the pilot. Pass 2 scale formula at lines ~198-210. Index setup at lines ~212-225 uses `central_lat = mean(y)` and pilot bandwidth. Cell loop lines ~256-290, same symmetric offsets.
- The `.max(0.1)` floor applies to `km_per_lon_degree` (km/deg), so the effective cos floor is `0.1/111.32`, not 0.1. The plan says "the floor on cos kept"; this plan keeps the existing expression.
- Current adaptive index uses `search_radius_deg` from pilot, and per-cell scale is in `[min, pilot]`, so the pilot-sized extent bounds every per-cell cutoff.
- Task 6.1.1 targets the `central_lat` block in `geodesic_kde_rust`. This task removes that block, so 6.1.1 may become a no-op (see Questions).

Offset bounding:
- Uncapped: `hw_max = max over grid lat of hw_lon` and `hw_lat` both `<= cell/1.5`, so `ceil(hw/cell) <= 1`. Offsets are at most 1 in each axis.
- Capped at 45 deg: `cell = 45` and offsets become `ceil(hw/45)`, which stays finite and correct, and grows only at very high latitude with large bandwidth.
- Offsets are computed from each point's own `hw`, so correctness does not depend on the cap.

Dateline argument:
- Data with `|x| > 90` is also stored at `x -/+ 360`. A grid point at lon g and contributor at lon c across +/-180 are then within one index-lon window when `|g - c_wrapped|` is within the lon offset, which holds whenever `hw_lon < 90` deg (the wrapped copy is always present for `|c| > 90`).
- Degenerate case: `hw_lon >= 90` deg (very high latitude with large bandwidth). A contributor with `|x| <= 90` at lon 0 and a grid point at 175 can then fall outside the stored-key window. Case (b) should use bandwidths where `hw_lon < 90`. Document the limit if a test is needed for the other case.

Risks:
- Lat bound uses 111.32 km/deg, but the true lat extent of a 3bw km arc is `3bw/111.195` deg (R = 6371.0088 km gives `pi*R/180 = 111.195`). A contributor due north at distance `d` in `[0.9989, 1.0) * 3bw` lies outside the box `3bw/111.32` and is missed. The 0.9 and 1.1 test cases do not reach this band. The spec's constant is used as written. Flagged in Questions.
- The linear lon bound `3bw/(111.32 cos(lat_grid))` is slightly below the exact great-circle extent `asin(sin r / cos lat)` at the same grid latitude (difference O(r^3)). Same concern as above, same band.
- Summation order changes with the per-point loops. Expect ~1e-15 differences, well under 1e-10.

## Amendments (coordinator, approved)

- Lat constant (Q1 = B): `R_km = 6371.0088`, `km_per_lat = R_km*pi/180` (about 111.195). Lat half-width = `3bw/km_per_lat`. Lon half-width = `3bw / max(km_per_lat*|cos(lat_grid)|, 0.1)`, the existing floor kept. Apply in both functions through one shared helper.
- Extra test cases: contributors at 0.999x the cutoff, due north and due east, at lat 40 and lat 65. The adaptive 0.999 case uses one grid point with `min = 0.5*pilot`, so the scale is exactly `0.75*pilot`.
- Cell cap at 45 deg: kept. Offsets are per point.
- Adaptive `min > pilot`: not touched. The R layer enforces `min < pilot`.
- Task 6.1.1 is covered here. Verify by grep that `central_lat` no longer appears in `geodesic_kde_rust`. Record 6.1.1 as done by 5.1.2. No separate edit.

- Stop rules unchanged. Any case above 1e-10 stops the task. A failing 0.999x case after the constant change stops the task.

## Questions (answered by coordinator; see Amendments)

1. Lat constant: the spec's `111.32` is slightly larger than the true km/deg for R = 6371.0088 km (111.195). Contributors at distance in `[~0.9989, 1.0) * cutoff` will be missed, so the brute-force tests can fail by more than 1e-10 at all latitudes. Options: (A) keep 111.32 as specified and add a 0.999x case to show the miss; (B) use the R-consistent `R*pi/180` for the search box only (a spec deviation, but the box stays conservative); (C) pad the half-widths by a small factor. Which?
2. Cell cap at 45 deg: spec says the cell must cover the largest half-width, but the cap at 45 can make `cell < hw`. Offsets stay correct (computed per point), so the cap is kept. Confirm.
3. Adaptive with `min_bandwidth > pilot_bandwidth`: scale can exceed pilot, and the pilot-sized index would then miss cutoffs. Does the R layer enforce `min <= pilot`? If not, this task should not touch it; flagging only.
4. Task 6.1.1 (remove the `central_lat` guard in `geodesic_kde_rust`) becomes moot once this task removes that block. Should 6.1.1 be marked done by 5.1.2, or left as a no-op?
5. The test file's current brute-force helpers, if any, are none (grep `bf_` finds nothing). Confirm the helper names above are acceptable.
