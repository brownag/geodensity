# 5.1.1 -- Search box uses the larger lon/lat radius (S2)

## Goal
Change the spatial search-box radius in `geodesic_kde_rust` and `geodesic_kde_adaptive_rust` from the MIN to the MAX of the lon and lat degree radii, so neighbors within 3 * bandwidth in longitude at high latitude are no longer dropped.

## Notes
Facts from Analysis:
- `search_radius_deg = search_radius_lon_deg.min(search_radius_lat_deg)` is present in both functions (lib.rs line 66 in `geodesic_kde_rust`, line 223 in `geodesic_kde_adaptive_rust`).
- Both derive `index_cell_size` from `search_radius_deg` (1.5x, clamped to [0.1, 45.0] in the adaptive function as well) and `search_radius_cells = ceil(search_radius_deg / index_cell_size)`, so they update automatically.
- `lon_deg = km / (111.32 * |cos lat|, floored at 0.1)` is always >= `lat_deg = km / 111.32`, so `min` always picks lat_deg today and `max` picks lon_deg. Practically, the change widens the box to lon_deg in both axes. The extra cells are cheap and the haversine check `dist_km < 3 * bandwidth` still filters, so results change only where neighbors were previously dropped.
- Risks:
  - Low-latitude results (30-50 deg) will also change, not just high latitude, because lon_deg/lat_deg = 1/cos(lat) is already 1.15-1.55 there. This is the "newly included neighbors" case that the escalation allows, but the fingerprints may shift more widely than the spec's "high latitude only" expectation. Expect this and report it.
  - Near the poles the 0.1 floor on cos makes lon_deg up to 10x lat_deg. The cell cap at 45 keeps the loop bounded (at most a few cells per side), so this is a performance note, not a correctness risk.
  - The adaptive function searches with `pilot_bandwidth_km` but the kernel cutoff uses each point's scaled bandwidth. Points with scale > 1 can still lose neighbors beyond 3 * pilot. This is pre-existing and out of scope for 5.1.1 (see Questions).
