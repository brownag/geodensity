It is reachable as `geodensity:::bandwidth_loocv_evaluate` through `R/extendr-wrappers.R:52`, which is in the namespace; NAMESPACE exports only `bandwidth_optimize`, `kde_adaptive`, `kde_geodesic`. No source change is needed.
- Rust LOOCV semantics that the brute force must match:
  - `kernel_norm = 1/(2*pi*bw^2)`, no `3*bw` cutoff, self excluded.
  - Floor: `max(density, 1e-10)`, then `ln`.
  - Return value is `sum(ll_i) / n_points`, the mean. Brute force must divide by n too, or the comparison fails.
  - Distances are geo haversine (`/1000`, km), with R = 6371008.8 m. `bf_haversine_km` uses R = 6371.0088 km, which is the same radius.
- Floor expectation: `log(1e-10) = -23.02585093`. For two far-apart points each density is exactly 0, so the mean is `log(1e-10)`. The tolerance is relative (tinytest), and `1e-12` is comfortable for a value this size.
- Test 34b uses `pmax(dens, 1e-10)` as the floor. Its degeneracy guard `all(dens > 1e-10)` makes the test show the score scale, not the floor.
- Pre-change behavior of the length-2 inputs: `!is.numeric(x) || x <= 0` errors in R 4.3+ with "'length = 2' in coercion to 'logical(1)'". The pattern "must be a single number" does not match, so step 10 is red before step 9.
- Risks:
  - Fixture size: the LOOCV is O(n^2 * n_bw). Keep n small (about 12 for 34b and 34c). Do not reuse the 150-point Test 31 fixture for many calls.
  - `bandwidth_optimize` warns when n < 3. Use at least 3 points in every call so no warning is emitted.
  - If 34b fails only at round-off, the cause is summation order, which is at most about 1e-15 relative. A larger mismatch is a real finding: stop.
