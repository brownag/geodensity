## Notes
- Analysis facts:
  - `haversine_distance_km` defined at lib.rs:19-32, radius `EARTH_RADIUS_KM = 6371.0`, uses `atan2` form of haversine.
  - Only call site: lib.rs:348-351 inside `bandwidth_loocv_evaluate` (line 336). Adaptive/fixed paths (lines 154, 304) already use `point.haversine_distance(&grid_point)` (meters) and `geo::Point::new` (lines 236, 291), so the imports already cover it.
  - geo `haversine_distance` (vendor `src/algorithm/haversine_distance.rs:46-55`): `c = 2 * asin(sqrt(a))`, radius `MEAN_EARTH_RADIUS` (6371008.8 m). Mathematically same formula as the helper (asin vs atan2 form is numerically equivalent to ~1e-16).
  - Test file ends at line 424 with `# Summary` / `cat("[YES] ...")`; no existing `bandwidth_optimize` test to clash with.
- Expected numeric effect: radius ratio 6371.0088 / 6371.0 = 1 + 1.38e-6. Every pairwise distance grows by a factor of ~1.00000138, so the kernel argument shifts by ~1.4e-6 relative. Log-likelihood change is roughly (d LL / d ln bw) * 1.4e-6 scaled by the distance-to-bandwidth sensitivity; for LL values of magnitude ~10-20 this is expected to be on the order of 1e-6 to 1e-5 absolute at most, i.e. borderline against tolerance 1e-5. Also the `bandwidth_opt` at 50 is a grid edge, so a tiny shift should not move it.
- Risk: if the baseline values were recorded with the old 6371.0 helper, the shift is real and may exceed 1e-5 for the largest-magnitude entries. Escalate per spec; do not widen tolerance.
- Risk: `bandwidth_optimize` is R-side and may reorder/convert output; confirm `res$log_likelihood` field name and `res$bandwidth_opt` exist before writing the assertion (read `R/geodensity.R` read-only).
- Out of scope and untouched: kernel math in `geodesic_kde_rust` / `geodesic_kde_adaptive_rust`, `R/geodensity.R`, `src/rust/vendor/`, `R/extendr-wrappers.R`.
